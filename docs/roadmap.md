## v1.0：自研 Mac agent（极致延迟与帧率）

系统屏幕共享够用但非极致。自研常驻 agent 可以达到"看视频级"流畅：

```
Mac agent (Swift):
  ScreenCaptureKit 采集 → VideoToolbox 硬编 H.264/HEVC
  → WebRTC（或 WebSocket+自定义协议）推流
  CGEvent 注入键鼠；launchd 常驻；只绑定 Tailscale 网卡 + token 鉴权
Android 端:
  MediaCodec 硬解 + SurfaceView 渲染（协议层继续复用本仓库 core 的设计）
```

## 网络层备选项：你的 AWS 服务器能派什么用场

默认方案 Tailscale 不需要任何自有服务器（它直接 NAT 打洞，打不通时走官方
DERP 中继）。自有 AWS 服务器在这些场景有价值：

1. **自建 DERP 中继（最实用）**：在国内直连 Mac 偶尔打洞失败时，流量会落到
   Tailscale 官方中继（多在海外，可能慢）。在你的 AWS（选离你近的区域，如
   宁夏/北京区或东京/新加坡）跑一个自建 DERP 节点并在 Tailscale ACL 里启用，
   中继路径就完全走你自己的服务器，延迟可控。数据本身是 WireGuard 端到端
   加密的，中继看不到内容。
2. **自建控制面 Headscale（彻底去第三方）**：用开源 Headscale 替代 Tailscale
   官方协调服务器，整个组网不依赖任何第三方账号。代价是要自己运维。
3. **未来 v1.0 的 WebRTC TURN/信令服务器**：自研 agent 走 WebRTC 时，打洞
   失败的兜底 TURN 服务器（coturn）正好部署在它上面。
4. **不推荐的用法**：用 frp 之类把 Mac 的 5900 端口经 AWS 转发到公网——VNC
   认证太弱，等于把 Mac 半裸暴露；如果一定要走自建隧道，至少用 WireGuard
   组网（AWS 当 hub），而不是裸端口转发。

结论：先不用 AWS，把 Tailscale 跑通；若实测经常走中继且卡顿，再按第 1 条
加自建 DERP，这是性价比最高的介入点。
